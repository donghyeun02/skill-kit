# gyeol (글결) — 한국어 글결 수렴기

한국어 글을 **레퍼런스 글의 목소리로 맞춥니다.** 사실·수치·고유명사·인용은 건드리지 않고 문장 길이, 명사화, 관용구, 종결 체계만 고칩니다.

"AI 티 제거"와는 목표가 다릅니다. 티를 지우는 일은 뺄셈이라서 끝까지 하면 밋밋한 글이 남습니다. gyeol은 지울 것보다 **지킬 것**을 먼저 정하고, 그 기준을 레퍼런스 글에서 직접 측정해 들고 있습니다. 고친 결과가 괜찮은지는 에이전트가 아니라 파이썬 게이트가 판정합니다.

## 설치

```
/plugin marketplace add donghyeun02/claude-kit
/plugin install gyeol@claude-kit
```

필요한 건 Python 3.10 이상뿐입니다. 스크립트는 표준 라이브러리만 씁니다.

> `epoko77-ai/im-not-ai`의 `humanize-korean`과 트리거가 겹칩니다. 서브에이전트는 description으로 자동 라우팅되니 둘을 같이 켜 두면 엉뚱한 쪽이 불릴 수 있습니다. 하나만 켜세요.

## 사용법

### 초안 다듬기 (사후)

```
글결 맞춰줘

[초안 붙여넣기]
```

경로는 자동으로 정해집니다. 강도를 직접 고를 수도 있습니다.

```
정밀하게 글결 맞춰줘      # heavy 고정 — 진단 → 윤문 → 게이트 → 마무리
가볍게 다듬어줘           # light 고정 — 윤문 1콜
```

### 쓰기 전에 규칙 보기 (사전)

```
글 쓰기 전 규칙 알려줘
```

`write-rules.md`(20개)를 그대로 보여주고 끝납니다. LLM 콜을 쓰지 않습니다.

### 결과가 마음에 안 들면

그대로 말하면 됩니다.

- "이 문단만 다시" — 해당 구간만 재실행
- "2차 윤문해줘" — 같은 run을 heavy로 다시. 윤문본이 아니라 **원문 기준으로** 다시 돕니다
- "더 보수적으로" — 확신 없는 구간은 원문 유지

### 내 글로 기준 바꾸기

```bash
python3 scripts/build_baseline.py --refs 내글1.txt 내글2.txt 내글3.txt \
    --output skills/gyeol/references/baseline.json --label "내 글"
```

레퍼런스는 2편 이상, 권장 3편 이상입니다. 바꾸면 게이트 임계가 전부 그 글들에서 다시 계산됩니다.

## 동작 방식

입력을 먼저 계량하고, 대역을 벗어난 축의 개수로 경로를 고릅니다. **글 길이는 경로를 바꾸지 않습니다.** 긴 글이 반드시 더 AI 같지는 않습니다.

| 경로 | LLM 콜 | 언제 | 흐름 |
|---|---|---|---|
| light | 1 | 이탈 축 0~1개. 이미 괜찮은 글 | 보수 강도 윤문 1콜. 거의 안 고쳤으면 "이미 좋습니다"로 조기 종료 |
| standard | 2 | 이탈 축 2~3개 | 진단 1콜 + 겨냥 윤문 1콜 |
| heavy | 3 | 이탈 축 4개 이상, 또는 "정밀하게" | 진단 → 윤문 → 마무리 |

```
입력
  ↓
prepare_input.py ── 챗봇 인사말 제거, 6축 계량, route_hint
  ↓
  ├─ light ──── rewriter ─────────────────────────┐
  ├─ standard ─ diagnostician → rewriter ─────────┤
  └─ heavy ──── diagnostician → rewriter ─────────┤
                                                  ↓
verify_gates.py ── 결정적 판정 (exit 0/1/2/3) ── LLM 콜 아님
  ↓
  exit 1 이거나 heavy → finalizer (원문 대조, 문제 문장만 국소 보정)
  exit 2 → 윤문본 채택 금지, 롤백 후 1회 재실행
```

### 에이전트

| 에이전트 | 경로 | 역할 |
|---|---|---|
| `gyeol-diagnostician` | standard · heavy | 이 글을 지배하는 패턴 3~6개를 룰북 ID로 진단. span을 세지 않음 |
| `gyeol-rewriter` | 전 경로 | 탐지·재작성·자체검증 6항을 한 콜에 |
| `gyeol-finalizer` | heavy · 게이트 경고 시 | 원문과 윤문본 대조. 전체 재작성 금지, 문제 문장만 |

진단 에이전트가 span 개수를 세지 않는 이유가 있습니다. "~에 대해가 몇 군데"를 LLM에게 세게 하면 같은 글에서 호출마다 값이 크게 흔들립니다. 세는 일은 스크립트가 하고, 에이전트는 "무엇이 이 글을 지배하는가"라는 판단만 합니다.

### 게이트 6축

| 축 | 판정 | 잡는 것 |
|---|---|---|
| 변경률 | 30% 경고 / 50% 중단 | 의미 드리프트 |
| 문장 길이 변동계수(CV) | 하한 | 문장이 전부 비슷한 길이로 평평해지는 것 |
| 한자어 명사화 밀도 | 상한 | "-성/-적/-화" + 하다/되다 |
| 결산 관용구 밀도 | 상한 | 결론적으로 · 따라서 · 이를 통해 |
| 종결 체계 혼용률 | 상한 | 해요체와 합니다체가 섞이는 것 |
| 인간 표지 유지율 | 원문 대비 80% | 구어 어미·1인칭·유보·자기비하를 깎는 것 |

마지막 축이 이 도구를 만든 이유입니다. 문자 기반 변경률은 구조 편집에 눈이 없어서, 구어 어미와 1인칭만 걷어낸 윤문은 글자를 거의 안 바꾸고 통과합니다. 의미는 그대로인데 사람 냄새만 빠진 글이 됩니다. 골든 픽스처 `02_marker_strip`에서 변경률은 **8.1%**로 통과 대역이었지만 유지율이 **14%**로 떨어져 exit 1로 잡혔습니다.

모든 임계는 `build_baseline.py`가 레퍼런스 글 분포에서 유도합니다. 손으로 적은 숫자가 없습니다.

### 룰북

`voice-rules.md` 하나가 원본이고, 여기서 두 파일이 생성됩니다.

| 파일 | 패턴 수 | 언제 |
|---|---|---|
| `write-rules.md` | 20 | 쓰기 전. 문장을 쓰는 순간 지킬 수 있는 것만 |
| `quick-rules.md` | 36 | 쓴 뒤. 밀도·분포·리듬 규칙 포함 |

"한 문단에 3회 이상" 같은 밀도 규칙은 사전 룰북에 들어갈 수 없습니다. 문단이 끝나기 전에는 이미 몇 번 썼는지 알 수 없어서, 넣으면 지킬 수 없는 지시가 됩니다. 이 조건은 테스트로 막아 뒀습니다.

| 카테고리 | 패턴 | 예 |
|---|---|---|
| V. 목소리 | 5 | 인간 표지를 깎지 마라, 문장 길이를 출렁이게, 막연한 긍정으로 닫지 마라 |
| T. 번역투 | 12 | "~에 있어서", "가지고 있다", 이중 피동, "~에 의해" |
| P. 관용구 | 6 | 결산 관용구, 안전 균형("장단점이 있다"), 형식명사 과다 |
| S. 구조·리듬 | 6 | 강제 3항 나열, 단문 일변도, 극적 단문 연타 |
| F. 형식·장식 | 5 | 볼드 라벨 불릿, 이모지, 한자어 명사화 |
| C. 챗봇 잔재 | 3 | 인사·마무리 문구, 지식 한계 면책 |

## 실행 예시

전형적인 LLM 초안(백엔드 블로그 "JPA N+1 문제")을 넣은 기록입니다. 대역 이탈 4축으로 heavy 경로가 골라졌습니다.

**Before**

> 물론입니다! 요청하신 블로그 글을 작성해 드리겠습니다:
>
> 백엔드 개발에 있어 성능 최적화는 매우 중요한 요소입니다. 특히 JPA를 사용하는 프로젝트에서는 N+1 문제가 빈번하게 발생하며, 이는 애플리케이션의 응답 속도에 치명적인 영향을 미칠 수 있습니다.
>
> 이러한 현상은 지연 로딩(Lazy Loading) 전략에 의해 발생됩니다. 지연 로딩은 실제로 데이터가 필요한 시점에 조회를 수행하는 방식으로, 불필요한 조회를 방지할 수 있다는 장점을 가지고 있습니다. 하지만 반복문 내에서 연관 엔티티에 접근하는 경우 오히려 성능 저하를 야기하게 됩니다.
>
> 결론적으로 N+1 문제는 JPA를 사용하는 개발자라면 반드시 이해하고 있어야 하는 핵심 개념이라고 할 수 있습니다. 이를 통해 보다 효율적인 애플리케이션을 구축할 수 있을 것입니다. 앞으로도 지속적인 학습을 통해 성장해 나가시길 바랍니다.
>
> 도움이 되셨길 바랍니다! 추가로 궁금한 점이 있으시면 말씀해 주세요.

**After**

> 백엔드에서 성능 최적화는 중요한데, 특히 JPA를 쓰는 프로젝트에서는 N+1 문제가 자주 생기고 애플리케이션 응답 속도에 치명적인 영향을 줍니다.
>
> 이 현상은 지연 로딩(Lazy Loading) 때문에 생깁니다. 지연 로딩은 데이터가 실제로 필요한 시점에 조회하는 방식이라 쓰지도 않을 데이터를 미리 가져오는 낭비를 막아 주지만, 반복문 안에서 연관 엔티티에 접근하면 접근할 때마다 쿼리가 나가면서 오히려 성능이 나빠집니다.
>
> N+1 문제는 JPA를 쓰는 개발자라면 반드시 이해하고 있어야 하는 개념입니다.

| 축 | Before | After |
|---|---|---|
| 문장 길이 CV | 0.270 | 0.565 |
| 한자어 명사화 | 0.0308 | 0.0102 |
| 결산 관용구 | 2 | 0 |
| 내용 앵커 (핵심 명사·수치) | — | 30/30 보존 |
| 변경률 | — | 32.2% (경고) |

이 실행에서 볼 만한 건 게이트가 **첫 윤문을 거부했다**는 점입니다. 목록을 산문으로 풀고 마지막 문단을 통째로 지운 1차본은 변경률 53%로 exit 2가 나왔고, 원문 구조를 살려 다시 쓴 뒤에야 통과 대역에 들어왔습니다. 에이전트가 스스로 채점했다면 1차본이 그대로 나갔을 겁니다.

남은 변경률 경고는 원문 대조로 확인했습니다. 삭제된 건 빈 수사("이를 통해 보다 효율적인…")와 덕담("앞으로도 지속적인 학습을…")이었고, 핵심 명사와 수치(10개·1개·11개)는 전부 남아 있었습니다.

인간 표지는 0.0 그대로입니다. 원문에 1인칭이나 경험 서술이 없었기 때문입니다. "제가 겪어보니" 같은 문장을 지어내면 없던 사실을 만드는 것이라 넣지 않았습니다. 목소리는 필자가 자기 경험을 채워야 생깁니다.

## 건드리지 않는 것

- 고유명사 · 제품명 · 기관명
- 수치 · 날짜 · 단위
- 발화 표지가 붙은 직접 인용(말했다 · 밝혔다 · 따르면)
- 코드 · 명령어 · 경로 · 식별자
- 업계 표준 약어(API · LLM · CI)
- 구어 어미 · 1인칭 · 유보 · 자기비하 표현

필자가 강조나 자문(自問)을 위해 따옴표로 감싼 문장은 필자 자신의 문장이므로 대상입니다.

## 알려진 한계

- **변경률 임계가 경로와 무관하게 30/50%입니다.** 이미 괜찮은 글을 지키려는 값이라, 많이 고치는 게 목적인 heavy 경로에서는 의미가 보존돼도 경고가 뜹니다. 위 예시가 그 경우입니다. 경로별로 나눌 예정입니다.
- **문장 길이 CV 하한이 장르에 따라 다르게 작동합니다.** 기본 레퍼런스가 회고·에세이라 150자 넘는 복문이 섞여 있는데, 기술 설명글에는 그런 문장이 드뭅니다. 기술 글 위주로 쓴다면 기술 글로 베이스라인을 다시 만드는 게 맞습니다.
- **인간 표지가 원래 없는 글에는 유지율 축이 작동하지 않습니다.** 0에서 0이면 100%로 계산됩니다. 보존 규칙이라 없는 표지를 만들어 넣으라고 요구하지 않으며, 그래서도 안 됩니다.
- 형태소 분석기를 쓰지 않고 접미사·어미 사전으로 근사합니다. 명사화 판정에 차단 목록(변화 · 문화 · 목적 등)이 있지만 빠진 낱말은 오탐이 날 수 있습니다.
- 기본 레퍼런스 3편 중 2편은 제3자 글이라 원문을 저장소에 넣지 않았습니다. 거기서 측정한 수치와 출처 URL만 있습니다. 그래서 CI에서는 베이스라인 재현 테스트가 건너뛰어지고, 로컬에서 원문을 받아 두면 전부 돕니다. 자세한 건 `tests/fixtures/README.md`에 있습니다.

## 개발

```bash
python3 scripts/build_rules.py            # 룰북 재생성
python3 scripts/build_rules.py --check    # 생성물이 원본과 맞는지 (CI)
python3 scripts/validate_package.py       # 버전·룰북·에이전트 정합성
python3 -m unittest discover -s tests     # 회귀 테스트
```

규칙은 `voice-rules.md`만 고치고 `build_rules.py`를 돌립니다. 생성물을 직접 고치면 다음 빌드에서 덮어써집니다. 이 저장소를 고칠 때 지켜야 할 계약은 `AGENTS.md`에 있습니다.
