# hardening — 레드팀/블루팀 감사와 연속 하드닝

코드를 공격자 입장에서 뒤져 문제를 찾고, **증거로 확인된 것만** 보고한 뒤, 승인한 것만 고칩니다. 커맨드는 두 개입니다.

`/redteam`은 한 번 돌리는 감사입니다. 보안·성능·품질 리뷰어 셋이 병렬로 찾고, 오케스트레이터가 CRITICAL/HIGH를 전부 직접 검증한 다음에야 보고서에 올립니다. `/harden`은 그 위에 점수를 붙인 반복 루프입니다. 한 사이클마다 한 차원을 공격하고, 전용 브랜치에서 고치고, 다시 채점해서 스코어보드에 남깁니다.

둘 다 내장 `general-purpose` 에이전트만 씁니다. 다른 플러그인이 없어도 돌아갑니다.

## 설치

```
/plugin marketplace add donghyeun02/skill-kit
/plugin install hardening@skill-kit
```

`/harden`은 `/redteam`의 절차를 재사용하므로 둘은 항상 같이 설치됩니다.

> `~/.claude/commands/`에 같은 이름의 원본 파일이 있으면 커맨드가 두 벌 뜹니다. 하나만 남기세요. 플러그인 쪽은 `/hardening:redteam`, `/hardening:harden`으로도 부를 수 있습니다.

## 사용법

### /redteam — 한 번 감사

```
/redteam                     # 커밋 안 된 변경분만
/redteam .                   # 프로젝트 전체
/redteam src/app/api         # 특정 경로
/redteam . --security        # 보안만 (--perf, --quality 조합 가능)
/redteam . --fix             # 승인 게이트 없이 CONFIRMED CRITICAL+HIGH 자동 수정
/redteam . --paranoid        # 지금은 도달 불가능한 잠재 이슈까지 보고
```

보고서가 나오면 멈추고 묻습니다.

```
무엇을 수정할까요? all / critical+high / 번호 지정(예: 1,2,5) / none
```

답하기 전에는 파일을 하나도 건드리지 않습니다. 수정 후에도 커밋·푸시는 하지 않습니다.

### /harden — 점수 기반 반복

```
/harden                               # 저장소 전체, security 차원
/harden . --dimension perf            # 성능
/harden . --dimension a11y --target 95
/harden . --branch hardening/sec-q3   # 작업 브랜치 지정
```

한 번 실행에 한 차원, 한 사이클입니다. 다음 사이클은 `/harden`을 다시 실행하면 됩니다.

## 동작 방식

### /redteam

```
범위 결정 + 스택 감지
    ↓
도달 가능성 분류 ── 아무도 import 하지 않는 파일은 DEAD. 거기서 나온 문제는 LOW로 상한
    ↓
레드팀 3인 병렬 ── security / perf / quality. 서로의 결과를 보지 않음
    ↓
검증 패스 (2.5) ── CRITICAL·HIGH를 오케스트레이터가 직접 확인. 못 증명하면 강등
    ↓
통합 보고서 ── 중복 제거, 근본 원인 묶기, 공격 체인 연결, 강등 내역 공개
    ↓
승인 게이트 ── 사용자가 고를 때까지 정지
    ↓
블루팀 수정 ── 최소 diff. 근본 원인 그룹은 한 번의 수정으로
    ↓
검증 ── 빌드·테스트·린트. 환경 때문에 못 돌리면 PASS가 아니라 "검증 불가"
```

### /harden

```
브랜치 안전장치 ── main/master 금지, hardening/<차원> 브랜치로 이동
    ↓
기준 점수 S₀
    ↓
레드팀 ── /redteam 절차를 극한 시나리오로 (공격 페이로드·극단 부하·키보드 전용 탐색)
    ↓
제안서 작성 ── docs/hardening/proposals/<날짜>-<차원>.md
    ↓
브랜치에서 수정
    ↓
재채점 S₁, Δ 계산
    ↓
스코어보드 기록 + 브랜치에 커밋 (푸시·PR 없음)
```

점수는 `clamp(100 − Σ 가중치, 0, 100)`이고 검증된 미해결 발견만 셉니다.

| 심각도 | 가중치 |
|---|---|
| CRITICAL | 25 |
| HIGH | 10 |
| MEDIUM | 4 |
| LOW | 1 |

같은 코드와 같은 검증 결과면 같은 점수가 나옵니다. 그래서 사이클 사이의 Δ를 믿을 수 있습니다.

## 원칙

**심각도는 증거로 얻는다.** `file:line`과 증거를 댈 수 없는 발견은 강등하거나 버립니다. 이론상 위험을 CRITICAL로 올리는 것도 결함으로 봅니다.

**지금 뚫리는 것과 모양만 위험한 것을 구분한다.** 아직 존재하지 않는 코드가 있어야 터지는 위험은 CRITICAL이 아니라 MEDIUM입니다.

**시크릿 노출은 프레임워크 기준으로 확인한다.** `NEXT_PUBLIC_`·`VITE_`·`REACT_APP_` 접두사가 붙었다고 곧 유출은 아닙니다. 클라이언트 코드가 참조하고 번들에 실제로 들어갔을 때만 유출입니다. `.env` 추적 여부, 소스 참조, 빌드 산출물, git 이력 순서로 확인하고 나서야 판정합니다.

**거짓 PASS도 거짓 경보다.** 빌드를 못 돌렸으면 "검증 불가"라고 씁니다. 측정 못 한 점수 상승은 기록하지 않습니다.

## 실행 예시 — 개인 블로그, security 1회차

Next.js 15 블로그에 `/harden`을 처음 돌린 기록입니다(2026-06-04).

```
기준 점수  62/100   (open: C1 · H0 · M3 · L1)
결과 점수  99/100   (Δ +37)
```

| 심각도 | 발견 | 처리 |
|---|---|---|
| CRITICAL | `api/local-mdx/route.ts` — 쿼리 파라미터가 검증 없이 `path.join` + `readFileSync`로 흘러감. `?file=../../../.env`로 시크릿을 읽을 수 있음 | 파일명 허용 목록 정규식 + `path.resolve` 경로 포함 검사 |
| MEDIUM | `.env` — Pinata 키에 `NEXT_PUBLIC_` 접두사 | 서버 전용 이름으로 변경. 교체(rotation)는 불필요 |
| MEDIUM | 퀴즈 컴포넌트의 `dangerouslySetInnerHTML` | 텍스트 렌더링으로 교체, 싱크 제거 |
| MEDIUM | `next.config.ts` 보안 헤더 없음 | HSTS·X-Frame-Options 등 5종 추가 |
| LOW | 원격 MDX `evaluate()` — import 하는 곳이 없는 죽은 코드 | 파일 삭제 |

두 가지가 눈여겨볼 만합니다.

첫째, 공격 체인입니다. path traversal 하나만 보면 파일 읽기 버그지만, `.env`의 시크릿과 묶이면 실제로 시크릿을 빼가는 경로가 됩니다. 보고서는 둘을 연결해서 체인의 실제 영향으로 평가했습니다.

둘째, Pinata 키 판정입니다. 초기 `/redteam` 실행에서 이 키를 CRITICAL로 과대 보고한 적이 있습니다. 그 뒤로 검증 패스와 시크릿 노출 확인 절차를 넣었고, 이 회차에서는 `src/`에서 참조 없음, `.next/static`에 없음, git 이력에 클라이언트 사용 없음을 확인해서 MEDIUM(잠재)으로 판정했습니다. 그래서 키 교체도 필요 없다고 정확히 말할 수 있었습니다.

남은 LOW 1건은 CSP입니다. AdSense·IPFS 게이트웨이·RPC·S3 이미지를 실제로 띄워 보며 맞춰야 해서, 잘못 걸면 라이브 사이트가 깨질 수 있어 다음 회차로 미뤘습니다. 99점에서 멈춘 이유입니다.

검증은 Node 22에서 `tsc --noEmit`와 `next build` 모두 통과했습니다. 로컬 Node 18.16에서는 빌드 자체가 안 돌아서, 그 환경에서는 "검증 불가"로 기록했을 것입니다.

## 산출물 (/harden)

| 파일 | 내용 |
|---|---|
| `docs/hardening/proposals/<날짜>-<차원>.md` | 레드팀 발견, 블루팀 제안과 예상 점수 기여, 이번에 미룬 것 |
| `docs/hardening/scoreboard.md` | 사이클당 한 줄. 수정 항목은 `#번호`가 아니라 짧은 라벨 + 심각도 |
| `docs/hardening/scoreboard.json` | 같은 내용의 기계 판독용 기록 (점수 전후, 수정 목록, 미해결 분포, 커밋) |

## 하지 않는 것

- main/master에서 작업하지 않습니다.
- 푸시하지 않고 PR을 열지 않습니다. 브랜치를 main에 올릴지는 사용자가 정합니다.
- 관계없는 미커밋 변경이 있으면 섞지 않고 멈춰서 묻습니다.
- 발견이 0건이면 0건이라고 씁니다. 문제를 지어내지 않습니다.

## 알려진 한계

- perf 차원은 앱이 떠야 Lighthouse 점수를 씁니다. 못 띄우면 가중치 공식으로 계산하고 "정적 추정"이라고 표시합니다.
- a11y는 AA 미준수를 HIGH, AAA 미준수를 LOW로 셉니다. 디자인 때문에 AA를 양보한 부분은 제안서에 따로 적어야 합니다.
- 사이클은 수동 실행입니다. `/loop`이나 `/schedule`로 자동화할 수 있지만 브랜치 전용·푸시 금지 안전장치는 그대로 둬야 합니다.
- 무거운 감사입니다. 저장할 때마다가 아니라 PR 전이나 기능을 끝냈을 때 돌리세요. 커밋마다 하는 시크릿 스캔은 pre-commit 훅이 맞습니다.

## 차원 추가하기

차원은 `{공격 기준, 수정 정책, 채점기}` 세 가지입니다. `seo`나 `bundle-size`를 넣으려면 레드팀에 극한 시나리오 기준을, 블루팀에 수정 정책을 주고, 0~100을 돌려주는 채점기를 정의하면 됩니다. 브랜치·제안서·스코어보드·보고 형식은 그대로 재사용합니다.
